# PullerView V2 — JPEG 画像への対応（2.0.11.0／タグ `V2-v12`）

作成: 2026-11-27

## 1. 内容

VisionView が扱う画像を BMP に加えて JPEG（.jpg／.jpeg）にも対応させた。

| 箇所 | 変更 |
|---|---|
| XG-X 受信フォルダの取り込み | .bmp に加えて .jpg／.jpeg を取り込む（これまで JPEG は警告を出して残していた）。.png／.tif は従来どおり取り込まない |
| 画像保存（[Image] folder） | 受け取ったデータをそのまま保存し、拡張子を中身に合わせる（JPEG → `YYYYMMDDHHMMSS_工程名.jpg`）。再圧縮しない。枚数上限・保存日数は BMP と JPG を合わせて数える |
| OK_SNAP／NG_SNAP | 同じく元の形式のまま保存。枚数は BMP と JPG の合計 |
| ファイル再生・模擬 XG-X・`--vision-test` | フォルダ内の .bmp／.jpg／.jpeg を対象にする |
| ファイル名からの時刻 | 従来の `yyyyMMddHHmmss…` に加えて、XG-X の出力名 `yyMMdd_HHmmss_…`（例 `261127_143305_0000005049_&Cam1Img.jpg`）も読む |

解析は従来から BMP 以外を GDI+ で展開する作りで、解析処理そのものは変えていない。
XgxBridge（Vapi.Net.dll の画像ロギング）が保存する形式は XG-X／Vapi 側で決まり、ブリッジは形式を指定していない。

## 2. 確認したこと（サンドボックス）

提供の JPEG 15 枚（5104×4092、約 416 KB／枚、NECK、探索枠 44,45,12,12）:

- 15 枚すべてでメニスカスを検出し、リングの当てはめに成功、晶線候補を検出。
- 受信フォルダからの取り込み → `…_NECK.jpg` で保存 → 受信フォルダから削除、BMP と混在時の枚数上限、.png を残すこと。

## 3. 注意・未確認

- **処理時間**: サンドボックスでは 1 枚あたり JPEG（5104×4092）約 430〜460 ms、BMP（1/2: 2552×2046）約 50 ms、BMP（原画）約 100 ms。JPEG は展開に時間がかかる。ファイルは小さいので転送・書込みは速くなるが、解析までの CPU 時間は増える。サンドボックス（Mono）の値であり、Windows 実機では未測定。
- **検出への影響**: JPEG では 1 枚あたりの晶線候補が 1〜3 本（特徴量 1.1〜4.6）で、BMP 11 枚（各 1 本）より多い。圧縮の影響か、撮影条件の違いかは、同じ場面の BMP と JPEG が無いため判別できていない。
- JPEG 展開時は 1 枚あたり約 63 MB（5104×4092×3）のメモリを使う。Windows 7 32bit 実機では未確認。
- CV5701（T1 電文）の経路は従来どおり BMP 前提（未変更）。
- Windows 実機、VS2022 でのビルドは未確認。
